Transformer based network architectures have shown excellent performance at autoregressive generation tasks i.e., adding onto and completing a given input sentence (prompt) one word at a time. This post uses all the neural network primitives discussed so far to assemble a network and trains it on the [TinyShakespeare](https://raw.githubusercontent.com/karpathy/char-rnn/master/data/tinyshakespeare/input.txt) dataset to generate text akin to writings of Shakepeare. The aim is to develop an intuitive understanding of the process of training a neural network in JAX and (hopefully) culminating in a fun toy model to keep as a personal Bard. :)

### Tokenization

Computers do not understand language and text in the traditional sense, they use numerical representations to work with them (think UTF encoding). Neural networks, essentially a computational graph of mathematical operationswork the same way. Tokenization is the process of breaking up continuous strings of text into smaller chunks, tokens. Depending on the strategy, these smaller chunks can be characters, words or sub-words. You might think words as token is a good strategy, after all it naturally breaks up text into smaller meaningful pieces that are composed into sentences and paragraphs. A major drawback of using words is the sheer number of unique tokens that will be in the vocabulary and ballon up the size of the model (recall, final layer of the network outputs a distribution over the entire vocabulary and each prior layer will have to be scaled accordingly to learn any meaningful relationship). Any word that model has not seen during its training will be a `<UNKNOWN>` token and thus, would lead to issues when this model is deployed in production. Character level encoding runs into the same problem as evident from the ~150k character encodings across all languages. Character encoding also forces the model to learn the complex task of spelling words in addition to learning the semantic relationship between those words.

#### GPT-2 Tokenizer

The GPT2 tokenizer (code from OpenAI available here) offers a reasonable middle ground. It is the Tokenizer used in the GPT2 model (groundbreaking performance on next word prediction at the time of release). Consider the sentence, `I'm learning AI!` as an example, It follows the below steps to convert text into numerical IDs:

1. **Regex Pre-splitting:** The tokenizer is opinionated and uses regex to split words in the text that are conducive to learning patterns in the English language. For instance, `'s`, `'ll`, `'ve` etc. are split from their base words so they are tokenized separately. This allows the model to treat these as additions to base words instead of "He'll" being treated as a unique word. Following similar reasoning, punctuations are separated from their preceding words and preceding space character is folded into the following word. Hence, the example sentence is broken up as: ["I", "'m", " learning", " AI", "!"].
2. **Byte level mapping:** Every character of the each element in the array obtained from the previous step is converted into its UTF8 encoding. Thus, each character is represented by a number from 0-256. Representing characters using raw bytes enables the tokenizer to handle characters from unseen languages thus solving the problem posed by `UNKNOWN` tokens but this also, introduces a new problem. Raw bytes for characters that are "unsafe", like `null`, `\n` etc. when being processed will cause issues. So, any character that is not strictly a visible character is shifted and represented by bytes corresponding to a visible character. Thus, our array from the previous step after this shifting becomes, ["I", "'m", "Ġlearning", "ĠAI", "!"]. Notice, the space character is shifted and it is represented by the byte encoding for `Ġ`. Thus, when interpreted all special characters are converted to a visible character and ASCII characters remain unchanged. See `byte_to_unicode` method in the GPT2 implementation for more details on which characters are unsafe.
3. **Byte-Pair encoding:** The next step is merging the most the frequent pairs of bytes. The tokenizer reads the entire input text and finds the pair of bytes that are most frequent and then mints a new token (ID > 256) that represents this new pair. Then it walks through the entire input and replaces each occurence of this pair with the newly minted token ID. This process is then repeated for the next most frequent pair of bytes in the input. This iterative approach of merging and minting new tokens is referred to as training the tokenizer as it gets better at concisely representing the entire input corpus after each step. GPT2 repeats this step 50000 times, hence the 256 base tokens from the previous step, 50000 newly minted byte pairs at each step and an additional `<endoftext>` token brings the total size of the tokeinzer vocabulary to 50257. The merging process is better due to regex pre-splitting since it prevents the tokenizer from making statistically frequent, but linguistically nonsensical, merges across unrelated word boundaries during the training process. The output of training is the `vocab` file consisting of 50257 numerical IDs for each unique token and a `merges` file that allows decoding from token ID to the pair of bytes it represents.

### Optimizer (Optax)

<div class="collapsiblecontainer">
<div class="collapsibleheader"><span>+ </span>What <code>optax.adamw</code> is doing</div>
<div class="collapsiblecontent" markdown="1">
An optimizer is the rule that turns gradients into an actual change in the weights. The gradient only says which direction increases the loss; it says nothing about how far to move. The simplest rule, plain gradient descent, is the one from the [first post in this series]({% post_url 2026-04-07-MachineLearningBeginning %}):

$$W \leftarrow W - \eta \nabla_W L$$

The step size $\eta$ is the learning rate, and it is unforgiving. Too large and each update overshoots the minimum it was aiming at, so the loss oscillates or diverges outright. Too small and training crawls, or settles into the first shallow dip it encounters. Worse, no single $\eta$ suits every parameter: a weight receiving consistently large gradients wants smaller steps than one that is barely updated at all, and the right scale changes as training progresses.

Adam[^adam] keeps a running estimate of the mean of each parameter's recent gradients and of their mean square, the uncentered second moment, and divides the step by the square root of that second moment, so every weight gets its own effective step size: parameters with large or erratic gradients are damped, parameters with small steady gradients are amplified. The `1e-3` passed above is still a learning rate and still sets the overall scale, so it has not disappeared, but the optimizer absorbs most of the per-parameter tuning that would otherwise have to be done by hand. The `W` in AdamW[^adamw] is decoupled weight decay, which shrinks weights directly during the update rather than by adding a penalty to the loss, the version that behaves correctly alongside Adam's per-parameter scaling. For a survey of these rules and what each one fixes about plain gradient descent, Ruder's overview[^ruder] is the clearest single reference.
